# AetherOS audit — 2026-08-12

Re-audit of the tree at `934e238`, covering the fifteen commits since the previous
audit's baseline (`445ba50`) — roughly 2,500 added lines, concentrated in the
scheduler, the syscall layer, the account database, and TCP. Those commits are
the fixes that closed the 2026-08-11 punch list, so this pass deliberately reads
the *fixes* rather than the code they replaced: H23 was a latent bug sitting in
code that looked correct, and the same risk applies to everything written since.

Findings say how they were established, using the previous audit's taxonomy:
**verified** = reproduced or measured directly, **code** = established by reading
the path, **plausible** = follows from the code but was not observed.

The headline is that the fixes hold up. Nothing here is a privilege escalation,
and the two authorization gates added in `04f0eab` (`sudo`, `passwd`) are sound on
re-reading. The real finding is a libc contract mismatch that silently disarms
the overflow guards in the account database.

## Medium

### N1 — `snprintf` returns the truncated length, so every overflow guard in `pwdb.c` is dead code
*verified*

`ctx_putc` (`user/libc/src/stdio.c:57`) advances the position counter only when it
actually writes a byte:

```c
static void ctx_putc(fmt_ctx_t *ctx, char c)
{
    if (ctx->buf) {
        if (ctx->pos + 1 < ctx->cap) ctx->buf[ctx->pos++] = c;
    } else {
        emit(c);
    }
}
```

`vfmt` returns `ctx->pos`, so `snprintf` reports how many bytes it *wrote*, not
how many it *would have* written. C99 requires the latter, and `pwdb.c` was
written against the C99 contract:

```c
len = snprintf(s_out + out, (size_t)(DB_MAX - out), "%s:%s\n", name, hash);
if (len <= 0 || out + len >= DB_MAX) return -1;    /* can never fire */
out += len;
```

With `cap = DB_MAX - out`, a truncated `len` is at most `cap - 1`, so
`out + len <= DB_MAX - 1` always. The guard is unreachable by construction. It
appears three times — `pw_add` (`pwdb.c:150`) and both `sh_set` branches
(`pwdb.c:224`, `pwdb.c:231`).

Verified on the host by compiling the real `user/libc/src/stdio.c` and calling it
with a 16-byte buffer and a 20-byte string:

```
cap=16 snprintf_returned=15 strlen(buf)=15  (C99 would return 20)
pwdb guard (out+len >= DB_MAX): DOES NOT FIRE   len=15
```

Consequence: instead of refusing, `passwd` and `useradd` silently write a
**truncated** `/etc/shadow` or `/etc/passwd` and report success. A lost shadow
line makes that account locked (`sh_get` fails, and `login` treats a missing hash
as locked); a lost passwd line makes the account vanish entirely. This is exactly
the failure mode `db_load` was written to prevent — its comment says a file that
fills the buffer "is an error rather than a silent truncation... which is what the
old per-tool 2 KiB parsers did" — reintroduced at the write side.

Reachability is bounded by `DB_MAX` (8192) and by these being root-only
operations: a shadow line runs about 95 bytes, so roughly 85 accounts brings the
file within one line of the ceiling. Data loss and account lockout, not
escalation.

The fix is in `ctx_putc`: count every byte and write only the ones that fit, so
the return value is the C99 would-be length. `stdio.c:139` already guards the NUL
write with `ctx->pos < ctx->cap`, which stays correct once `pos` can exceed `cap`.

## Low

### N2 — the sleeper-expiry loop requeues a thread that may still be running on another CPU
*code; not reproduced in 200,000 attempts*

`sched_wake` goes to real trouble to avoid enqueuing a thread that has not yet
saved its context, and says why:

```c
while (t->on_cpu) { __asm__ volatile("pause" ::: "memory"); }
```

> Enqueuing the thread before it has saved its context would let a third CPU
> resume it on its still-live stack.

The sleeper-expiry loop in `schedule()` promotes a thread on the same transition
(`THREAD_BLOCKED` → `THREAD_READY` → `rq_add`) with no such check. The asymmetry
is visible in the code: the loop tests `on_cpu` for the `THREAD_DEAD` case one
branch below, and not for the `THREAD_BLOCKED` case.

The window is in `sched_sleep_ms`, which links itself onto the sleep list and
marks itself `BLOCKED` while still executing, and only then yields:

```c
t->sleep_deadline = apic_now_tsc() + ms * apic_tsc_per_ms();
t->state          = THREAD_BLOCKED;
t->sleep_next     = sleep_head;
sleep_head        = t;
spinlock_release(&rq_lock);
SCHED_YIELD();               /* <- another CPU can run the sleeper loop here */
```

`sys_sleep` passes the user's millisecond count straight through
(`syscall.c:1016`), so `sleep(0)` produces a deadline that has *already* expired
inside that window. Another CPU running the loop there would unlink the thread,
mark it READY, and could dispatch it off a stale `rsp` — two CPUs executing on one
64 KiB kernel stack.

Measured rather than assumed: instrumenting the loop to count how often it saw an
expired sleeper still flagged `on_cpu`, over 200,000 `sleep(0)` calls on a 2-vCPU
guest, gave **0 cross-CPU and 200,000 same-CPU**. The same-CPU case is the thread
yielding into its own `schedule()`, which is harmless — `cur->rsp` is written at
the top of `schedule()` before the loop runs. So the dangerous interleaving is
real by inspection but was not observed, and the severity is set accordingly.

Guarded in this commit: the loop now skips a sleeper that is `on_cpu` and is not
`cur`, leaving it linked for a later tick. `st != cur` matters — holding the
same-CPU case back would cost every zero-length sleep a full tick of latency for
no safety gain.

### N3 — a 64-bit file descriptor is truncated to `int` instead of rejected
*code*

`sys_read`, `sys_write` and `sys_close` take `fd` as `uint64_t` and pass `(int)fd`
to the fd-table helpers (e.g. `syscall.c:328`). `read(0x100000003, ...)` truncates
to 3 and operates on the caller's fd 3 rather than returning `EBADF`.

Not a privilege issue: `fd.c` bounds-checks every index against `MAX_FDS`, and the
truncated value can only ever name a descriptor the caller already owns. It is a
correctness wart — a program with a corrupt fd value gets silent misdirection
instead of an error.

### N4 — `sudoers_allows` silently ignores anything past 2047 bytes
*code*

`user/bin/sudo.c:42` reads at most `SUDOERS_MAX - 1` bytes and parses only that.
An account listed past the cut is not found, so it is denied — the failure is
closed, which is the right direction, but it is silent. Same shape as L17 in the
previous audit, which was fixed for `/etc/passwd` by giving `pwdb.c` an explicit
too-large error; `sudo` still has its own private parser and its own private
limit.

### N5 — stale comment in `syscall_dispatch` contradicts the code beneath it
*code*

`syscall.c:1078` says the deferred-kill path runs when "the process is already
marked exited, so nothing here touches it". It is not: `process_kill` returns
early — before `process_mark_exited` — precisely when `sched_kill` defers
(`process.c:292`). The very next comment says so correctly ("process_kill left the
process untouched... so do the whole teardown here"), and the code does the right
thing. Only the first comment is wrong, but it describes the opposite of the
invariant the path depends on, which is the kind of thing that gets trusted during
the next edit.

## Checked and found sound

Recording these so the next pass does not re-derive them:

- **`sudo`'s two gates** (`04f0eab`). Authorization is checked before
  authentication; both use the **real** uid, correct for a setuid-root binary; a
  missing or unreadable `/etc/sudoers` denies everyone but root; a locked account
  cannot pass. `spawn_as` is reached only after both gates.
- **`passwd`'s authorization.** Real-uid checks throughout, non-root must retype
  the current password, a locked account cannot be unlocked except by root, and
  empty passwords are refused explicitly (an empty hash means locked).
- **`sys_kill`'s permission check** (`syscall.c:1022`): a non-root caller may only
  kill a process with a matching real uid.
- **`sys_spawn_as`** is gated on `euid == 0`, and the child is created parked so it
  never executes with the parent's root credentials before being dropped.
- **Installed modes** (`scripts/make-disk.sh`): `sudo`/`passwd` `04755`,
  `/etc/passwd` `0644`, `/etc/shadow` `0600`, `/etc/sudoers` `0600` — all as
  documented.
- **The KDF** (`crypt.c`). Salt and password are fed back in every round, so work
  cannot be precomputed per salt; the compare is constant time over the whole
  stored string; malformed and over-long salts fail closed. Salts remain unique
  but not unpredictable (`rdtsc` + counter), which is a known and documented
  limitation, not a new finding.
- **`copy_to_user` / `copy_from_user`** validate the range before the copy and use
  an exception-table fixup, and both close the SMAP window on the fault path.
- **Lock discipline for the reaper.** `schedule()` calls `kfree` and
  `vmm_space_destroy` from the ISR path; both `heap_lock` and `pmm_lock` are
  IRQ-safe (`spinlock_acquire_irqsave`), so a thread preempted mid-allocation
  cannot deadlock the reaper on the same CPU.
- **`mutex_lock`'s block/yield window.** Marking `BLOCKED` before dropping the
  spinlock, and the `cli` before `SCHED_YIELD`, leave no interleaving where a
  concurrent `mutex_unlock` loses or double-enqueues the waiter; `wait_next` is
  cleared by the unlocker, so sharing it with the process wait queue is safe.
- **TCP retransmission** (`2529a32`). `send_reliable` rewinds `snd_seq` before each
  resend, checks the ACK before sleeping, and stops retrying when the peer leaves
  ESTABLISHED. One wart, not worth a finding on its own: `tcp_connect`'s retry
  loop re-tests `state == TCP_SYN_SENT` only at the top of each attempt, so a
  SYN-ACK arriving mid-iteration can still produce one duplicate SYN.

## Not re-audited

The unchanged surface — ext2, AHCI/NVMe, xHCI/USB, the GUI, ACPI, SMP bring-up —
was outside this pass's scope. The previous audit's Known Limitations in
`CLAUDE.md` still stand, in particular: no receive reassembly in TCP, no fork/exec,
Ctrl+C delivered by polling rather than signals, and a thread killed while waiting
in a mutex or process wait queue leaking its struct and stack by design.
