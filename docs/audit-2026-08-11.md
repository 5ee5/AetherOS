# AetherOS audit — 2026-08-11

Re-audit of the tree at commit `445ba50`, after the seven fix commits that closed
the previous punch list (items 1–9). Findings are ranked by severity. Each says
how it was established: **verified** = reproduced in QEMU, **code** = established
by reading the path, **plausible** = a consequence that follows from the code but
was not observed.

## Critical

### C1 — `sudo` grants root to any user, with no authorization and often no authentication
*verified*

`user/bin/sudo.c` never reads `/etc/sudoers` — there is no reference to that file
anywhere in the tree (`grep -rn sudoers` → no hits), though `CLAUDE.md` documents
one. It looks the caller up in `/etc/passwd`, prompts for *their own* password,
and on a match calls `spawn_as(argv[1], &argv[1], 0, 0)`. So every user who knows
their own password has full root.

Worse, `sudo.c:59` skips the prompt entirely when the stored password is empty,
and `useradd` writes new accounts with an empty password field
(`user/bin/useradd.c:73`, `"%s::%u:%u:%s\n"`). Every account `useradd` creates is
therefore an unauthenticated root escalation until someone runs `passwd`.

Reproduced from a clean boot:

```
/root # useradd bob
User 'bob' created (uid=1000). Use 'passwd bob' to set a password.
/root # exit
AetherOS login: bob
Password:               <- empty, accepted
/home/bob $ id
uid=1000 gid=1000
/home/bob $ sudo /bin/id
uid=0(root) gid=0(root)
/home/bob $ sudo /bin/useradd eve
User 'eve' created (uid=1001).
```

Files: `user/bin/sudo.c:53-74`, `user/bin/useradd.c:73`,
`scripts/make-disk.sh:42-45` (installs `/bin/sudo` mode 04755).

## High

### H2 — `kill` on a sleeping process does not kill it; the process resumes later
*code; UAF consequence plausible*

`process_kill` (`kernel/proc/process.c:222-230`) marks the victim's thread
`THREAD_DEAD` from another thread's context. A thread that is *blocked* is not on
the run queue, so it is never reaped — and the sleeper-wake loop in
`sched_tick` (`kernel/sched/sched.c:185-189`) sets `state = THREAD_READY` and
re-queues it with no `THREAD_DEAD` check. The "killed" process resumes executing
user code when its sleep deadline expires.

By then `process_mark_exited` has already published `exited`, so the parent's
`waitpid` has returned and called `process_reap` → `kfree(proc)`. The resurrected
thread runs with a dangling `t->process`, and its eventual `sys_exit` writes
through it (`process_close_all_fds`, `process_mark_exited`) — a use-after-free on
the kernel heap, which a subsequent spawn is likely to have recycled into another
process's struct.

The same shape applies to a victim blocked on a mutex wait queue: it stays linked
in `m->waiters`, and a later `mutex_unlock` pops it and calls `sched_wake` on a
thread that may already be freed.

Verified so far: `kill` on a sleeping background job marks it exited and it
disappears from `ps`. A 25-second session afterwards showed no crash, so the
memory-corruption consequence is reasoned, not observed.

Related, same root cause: a victim killed while holding `vfs_lock` never releases
it, wedging the filesystem for every process on the system.

### H3 — `read()` on a socket reads the keyboard
*code*

`fd_alloc_socket` (`kernel/proc/fd.c:26-36`) allocates from fd **0**, while
`fd_alloc` and `fd_alloc_pipe` both start at 3 to reserve stdio
(`fd.c:12-24`, `fd.c:62-70`). The first socket in a fresh process therefore gets
fd 0 — and `sys_read` special-cases fd 0 as console input *before* consulting the
fd type (`kernel/syscall/syscall.c:262-276`). `wget` calls `read(fd, ...)` on its
socket (`user/bin/wget.c:102`), so it reads the keyboard instead of the network.
`write` happens to work, because `sys_write` checks the type for anything that
isn't fd 1 or 2.

### H4 — the parent's Ctrl+C poll eats the child's stdin
*code*

`sys_waitpid` consumes a character from serial and the input ring on every loop
iteration and discards anything that isn't `0x03`
(`kernel/syscall/syscall.c:391-392`), while the running child reads the same two
sources in `sys_read_stdin` (`syscall.c:227-251`). Any interactive child loses
keystrokes to its waiting parent.

### H5 — `/etc/passwd` is mode 0600, so no unprivileged tool can resolve names
*verified*

The image installs `/etc/passwd` root-owned 0600 (`scripts/make-disk.sh:51`).
`whoami` and `id` cannot read it, so they print bare numbers — `whoami` as bob
printed `1000`. Unix keeps `/etc/passwd` world-readable *because* it holds no
secrets; the secrets belong in `/etc/shadow` at 0600.

## Medium

- **M6** — short writes reported as complete. `sys_write` ignores partial
  `vfs_write` / `sock_send` results and returns the full count
  (`syscall.c:167-181`): silent data loss on a full disk or full socket buffer.
- **M7** — unbounded kernel allocation from a user-supplied size:
  `sys_listdir` (`syscall.c:679`) and `sys_ps` (`syscall.c:908`) `kmalloc` a
  caller-chosen length with no cap. Heap-exhaustion DoS from an unprivileged
  process.
- **M8** — kernel panics on user-triggerable OOM. `alloc_thread` and the
  `thread_create*` stack allocations panic on `kmalloc` failure
  (`kernel/sched/thread.c:47-52,81,121,138`) instead of failing the syscall, so a
  spawn loop halts the machine.
- **M9** — process-table exhaustion silently "succeeds". With all
  `MAX_PROCS` slots full, `process_create_from_result` never publishes the
  process (`process.c:186-188`) but returns and starts it anyway: invisible to
  `ps`, unwaitable, never reaped.
- **M10** — `sudo` does not resolve `/bin`, so `sudo whoami` fails and only
  absolute paths work (*verified*).
- **M11** — `passwd` truncates `/etc/passwd`. It reads at most 2047 bytes
  (`passwd.c:10,59`) and rewrites the file from that truncated copy, destroying
  accounts past the limit; individual lines over 255 bytes are also truncated
  (`passwd.c:111-115`).
- **M12** — `process_ps` walks `s_procs[]` without `proc_table_lock`
  (`process.c:256`), so it can read a struct that is being freed.
- **M13** — setuid bits are never cleared on write or on a chmod by the owner,
  so a root-owned setuid binary that is group- or world-writable can be rewritten
  by an unprivileged user.

## Low

- **L14** — `stat` prints a literal `(%04o)`: tinylibc's printf has no `%o`
  conversion (`user/bin/stat.c:39`, `user/libc/src/stdio.c:106-120`).
- **L15** — `sys_read` on a socket spins forever if the peer never sends
  (`syscall.c:823`); no timeout.
- **L16** — `CLAUDE.md` drift: `sys_sleep` is described as a busy-wait but blocks
  properly (`sched.c:232-248`); `sudo` is documented as checking `/etc/sudoers`,
  which does not exist; the dead `ps2kbd_getchar`/`ps2kbd_ready` accessors are
  documented rather than deleted.
- **L17** — `login` and `passwd` read only the first 2047 bytes of `/etc/passwd`;
  later entries are invisible (`login.c:18`).
