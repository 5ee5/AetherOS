# AetherOS audit — 2026-08-11

Re-audit of the tree at commit `445ba50`, after the seven fix commits that closed
the previous punch list (items 1–9). Findings are ranked by severity. Each says
how it was established: **verified** = reproduced in QEMU, **code** = established
by reading the path, **plausible** = a consequence that follows from the code but
was not observed.

## Critical

### C1 — `sudo` grants root to any user, with no authorization and often no authentication
*verified*

`user/bin/sudo.c` never reads `/etc/sudoers` — there is no reference to that file
anywhere in the tree (`grep -rn sudoers` → no hits), though `CLAUDE.md` documents
one. It looks the caller up in `/etc/passwd`, prompts for *their own* password,
and on a match calls `spawn_as(argv[1], &argv[1], 0, 0)`. So every user who knows
their own password has full root.

Worse, `sudo.c:59` skips the prompt entirely when the stored password is empty,
and `useradd` writes new accounts with an empty password field
(`user/bin/useradd.c:73`, `"%s::%u:%u:%s\n"`). Every account `useradd` creates is
therefore an unauthenticated root escalation until someone runs `passwd`.

Reproduced from a clean boot:

```
/root # useradd bob
User 'bob' created (uid=1000). Use 'passwd bob' to set a password.
/root # exit
AetherOS login: bob
Password:               <- empty, accepted
/home/bob $ id
uid=1000 gid=1000
/home/bob $ sudo /bin/id
uid=0(root) gid=0(root)
/home/bob $ sudo /bin/useradd eve
User 'eve' created (uid=1001).
```

Files: `user/bin/sudo.c:53-74`, `user/bin/useradd.c:73`,
`scripts/make-disk.sh:42-45` (installs `/bin/sudo` mode 04755).

**Fixed** in `04f0eab`: hashes moved to a 0600 `/etc/shadow` (salted, iterated
SHA-256), `sudo` now requires both `/etc/sudoers` membership and a re-entered
password and fails closed when the file is missing, and `useradd` creates
accounts locked. Re-verified in QEMU.

## High

### H2 — `kill` on a sleeping process does not kill it; the process resumes later
*code; UAF consequence plausible*

`process_kill` (`kernel/proc/process.c:222-230`) marks the victim's thread
`THREAD_DEAD` from another thread's context. A thread that is *blocked* is not on
the run queue, so it is never reaped — and the sleeper-wake loop in
`sched_tick` (`kernel/sched/sched.c:185-189`) sets `state = THREAD_READY` and
re-queues it with no `THREAD_DEAD` check. The "killed" process resumes executing
user code when its sleep deadline expires.

By then `process_mark_exited` has already published `exited`, so the parent's
`waitpid` has returned and called `process_reap` → `kfree(proc)`. The resurrected
thread runs with a dangling `t->process`, and its eventual `sys_exit` writes
through it (`process_close_all_fds`, `process_mark_exited`) — a use-after-free on
the kernel heap, which a subsequent spawn is likely to have recycled into another
process's struct.

The same shape applies to a victim blocked on a mutex wait queue: it stays linked
in `m->waiters`, and a later `mutex_unlock` pops it and calls `sched_wake` on a
thread that may already be freed.

Verified so far: `kill` on a sleeping background job marks it exited and it
disappears from `ps`. A 25-second session afterwards showed no crash, so the
memory-corruption consequence is reasoned, not observed.

Related, same root cause: a victim killed while holding `vfs_lock` never releases
it, wedging the filesystem for every process on the system.

**Fixed**, and the resurrection is now reproducible-then-absent rather than
reasoned. The rule is that `THREAD_DEAD` is terminal:

- `sched_wake` promotes only a `THREAD_BLOCKED` thread, so neither a
  `mutex_unlock` nor an exit notification can resurrect a corpse — and a thread
  already runnable is never enqueued twice.
- the sleeper loop unlinks unconditionally but re-queues only a still-`BLOCKED`
  thread; a dead sleeper goes to the reaper instead of the run queue.
- the dispatcher drops a dead thread found in the run queue rather than
  `iretq`-ing into it.
- new `sched_kill` replaces the bare `state = THREAD_DEAD` store in
  `process_kill`: it takes `rq_lock` (so it cannot race a transition in
  `sched_tick`) and pulls the victim off the sleep list in the same breath.
- `process_kill` now kills the thread *before* publishing the exit status, so the
  parent's `waitpid` can no longer free the process struct under a live thread,
  and clears `proc->thread` afterwards.
- the thread reaper no longer reads `t->process` at all to decide orphan status —
  that was a use-after-free on the ordinary exit path too, since a parent's
  `waitpid` can free the struct first. `sys_exit` and `process_kill` collect an
  orphan themselves, while the process is still known to be live.

Verified in QEMU: five sleeping background jobs killed with `kill`, all gone from
`ps`, none resumed, filesystem and shell healthy afterwards; `ktest [sched]`
asserts that a thread killed while sleeping never runs its remaining code.

The stranded-lock half was fixed separately in `a7e6d20`. Threads count the
mutexes they hold, and `sched_kill` refuses to terminate one holding any: it flags
the thread, which then dies at its next syscall return, once the operation has
finished and released everything. Releasing the lock on the victim's behalf was
rejected as a fix — it would publish whatever half-written metadata the operation
was in the middle of. `process_kill` leaves the process untouched in that case, so
the parent's `waitpid` cannot free the struct under a live thread; the victim does
its own teardown. `ktest [sched]` asserts a lock holder cannot be killed, survives
to unlock, and leaves the mutex acquirable. Verified live by interrupting a 2 MB
copy: the deferral fires and the filesystem stays healthy across repeat runs.

One part remains open by choice: a thread killed while *waiting* in a mutex or
process wait queue keeps its struct and 64 KiB stack, because freeing it would
leave that queue pointing at freed memory. It never runs again (`sched_wake`
refuses it) and the kernel logs the leak. Reproduced with `kill 2` against a
`login` blocked in `waitpid`.

Note on the wedge: it is argued from the code, not reproduced. A run I first read
as a wedge turned out to be `H22` below, and once that was fixed I could not
produce a wedge to compare against.

### H3 — `read()` on a socket reads the keyboard
*code*

`fd_alloc_socket` (`kernel/proc/fd.c:26-36`) allocates from fd **0**, while
`fd_alloc` and `fd_alloc_pipe` both start at 3 to reserve stdio
(`fd.c:12-24`, `fd.c:62-70`). The first socket in a fresh process therefore gets
fd 0 — and `sys_read` special-cases fd 0 as console input *before* consulting the
fd type (`kernel/syscall/syscall.c:262-276`). `wget` calls `read(fd, ...)` on its
socket (`user/bin/wget.c:102`), so it reads the keyboard instead of the network.
`write` happens to work, because `sys_write` checks the type for anything that
isn't fd 1 or 2.

**Fixed.** All three allocators now share `fd_alloc_slot`, which starts at 3, and
both `sys_read` and `sys_write` resolve the fd type *before* special-casing
0/1/2 — the console is now only the fallback for a stdio fd with nothing
installed on it, so no descriptor can ever be served the wrong object again.
Fixing it uncovered two further bugs on the socket read path, which had never
been reachable from userland (H3a, H3b below). `wget http://example.com/` now
prints the page; the fd floor is asserted by `ktest [proc]`.

### H3a — IP payload length taken from the Ethernet frame, not the IP header
*verified (packet capture)*

`ipv4_recv` computed `plen = len - ihl` from the frame it was handed
(`kernel/net/ipv4.c:41-42`), ignoring the header's `total_length`. Ethernet pads
every frame to 60 bytes, so a bare TCP ACK (14 + 20 + 20 = 54) arrives with 6
trailing zero bytes — which TCP accepted as 6 bytes of payload and added to
`rcv_nxt`. The peer's next, genuine segment then failed the `seq == rcv_nxt`
test in `tcp_input` and was dropped as out-of-order: an HTTP response was
ACKed by sequence number but never delivered to the application. Confirmed on
the wire — the guest ACKed `+6` before the response had even arrived, then the
server retransmitted the whole body indefinitely.

**Fixed.** `ipv4_recv` now derives the payload length from `total_length` and
drops malformed or truncated frames.

### H3b — `tcp_recv` discards buffered data once the peer sends FIN
*verified (packet capture)*

`tcp_recv` returned 0 whenever the state was not `TCP_ESTABLISHED`, throwing
away whatever was still in `rxbuf`. Because the FIN of a `Connection: close`
HTTP response normally arrives while the body is still buffered and unread, the
handler's move to `TCP_CLOSED` truncated every transfer at whatever the last
`read()` happened to leave behind.

**Fixed.** `tcp_recv` drains the buffer regardless of state; EOF is decided one
layer up in `sock_recv`, which already required an empty buffer *and* a dead
connection.

### H4 — the parent's Ctrl+C poll eats the child's stdin
*verified*

`sys_waitpid` consumes a character from serial and the input ring on every loop
iteration and discards anything that isn't `0x03`
(`kernel/syscall/syscall.c:391-392`), while the running child reads the same two
sources in `sys_read_stdin` (`syscall.c:227-251`). Any interactive child loses
keystrokes to its waiting parent.

Reproduced twice over serial: typing `ps` reached the shell as `s`
(`command not found`), and `echo T-END` arrived as `cho T-END`.

**Fixed.** Serial is now drained *into* the shared input ring (`console_fill`)
rather than read alongside it, so the console is one ordered queue with one
consumer; `sys_waitpid` uses a new non-destructive `input_peek` and dequeues only
the byte it acts on.

Fixing the theft exposed that the poll was nearly useless anyway: `process_wait`
blocked until the child exited, so the Ctrl+C check ran **once per spawn** and
Ctrl+C did nothing to a running child (no `^C` ever appeared, and `sleep 60`
could not be interrupted). `process_wait` is now `process_wait_timeout`, which
blocks on the exit notification *and* a 50 ms deadline, so the check actually
runs. Verified: `^C` interrupts a sleeping child and the shell survives.

### H5 — `/etc/passwd` is mode 0600, so no unprivileged tool can resolve names
*verified*

The image installs `/etc/passwd` root-owned 0600 (`scripts/make-disk.sh:51`).
`whoami` and `id` cannot read it, so they print bare numbers — `whoami` as bob
printed `1000`. Unix keeps `/etc/passwd` world-readable *because* it holds no
secrets; the secrets belong in `/etc/shadow` at 0600.

**Fixed** in `04f0eab`: `/etc/passwd` is 0644 and carries `x` in place of every
hash; `/etc/shadow` holds the hashes at 0600.

## Medium

- **M6** — short writes reported as complete. `sys_write` ignores partial
  `vfs_write` / `sock_send` results and returns the full count
  (`syscall.c:167-181`): silent data loss on a full disk or full socket buffer.
  **Fixed** in `ebaba82`: each sink reports what it took and `sys_write` returns
  that. tinylibc gained `write_all`, and cp / the shell's `>` / wget's request send
  now report failure instead of truncating. Verified on an image with 5 KiB free.
- **M7** — unbounded kernel allocation from a user-supplied size:
  `sys_listdir` (`syscall.c:679`) and `sys_ps` (`syscall.c:908`) `kmalloc` a
  caller-chosen length with no cap. Heap-exhaustion DoS from an unprivileged
  process. **Fixed** in `9cbaaaf`: both clamp to 64 KiB.
- **M8** — kernel panics on user-triggerable OOM. `alloc_thread` and the
  `thread_create*` stack allocations panic on `kmalloc` failure
  (`kernel/sched/thread.c:47-52,81,121,138`) instead of failing the syscall, so a
  spawn loop halts the machine. **Fixed** in `9cbaaaf`: they return NULL and the
  syscall fails with -EAGAIN. The two boot-time paths that cannot continue without
  a thread still panic, deliberately.
- **M9** — process-table exhaustion silently "succeeds". With all
  `MAX_PROCS` slots full, `process_create_from_result` never publishes the
  process (`process.c:186-188`) but returns and starts it anyway: invisible to
  `ps`, unwaitable, never reaped. **Fixed** in `9cbaaaf`: creation is refused, and
  every failure path frees the address space it was handed. Asserted by
  `ktest [proc]`, which fills the table and checks the next attempt is refused
  without leaking.
- **M10** — `sudo` does not resolve `/bin`, so `sudo whoami` fails and only
  absolute paths work (*verified*). **Fixed** in `04f0eab`.
- **M11** — `passwd` truncates `/etc/passwd`. It reads at most 2047 bytes
  (`passwd.c:10,59`) and rewrites the file from that truncated copy, destroying
  accounts past the limit; individual lines over 255 bytes are also truncated
  (`passwd.c:111-115`).
- **M12** — `process_ps` walks `s_procs[]` without `proc_table_lock`
  (`process.c:256`), so it can read a struct that is being freed. **Fixed** in
  `9cbaaaf`.
- **M13** — setuid bits are never cleared on write or on a chmod by the owner,
  so a root-owned setuid binary that is group- or world-writable can be rewritten
  by an unprivileged user. **Fixed** in `479d70e`: `sys_open` strips
  setuid/setgid when a non-root process asks for a writable descriptor, and
  `sys_chmod` will not leave setgid on a file whose group the caller is not in.
  Reproduced (bob rewriting a root-owned 4777 binary) and confirmed fixed.

### M18 — the APIC timer runs ~3× fast, so every duration is ~3× short
*verified (timed against the host clock)*

`sleep 30` in the guest returns after **10.0 s** of wall-clock time, measured by
timestamping the serial log around `echo T-START; sleep 30; echo T-END`. Since
`sched_sleep_ms` sets `deadline = g_ticks + ms` and `g_ticks` counts timer
interrupts, the APIC timer is firing at roughly 3 kHz rather than the ~1 kHz
`apic_timer_init` calibrates for (`kernel/arch/x86_64/apic.c`). Everything derived
from ticks is wrong by the same factor: `sleep`, the scheduler's time slice, the
desktop clock, and every driver timeout expressed in milliseconds. Measured under
QEMU/TCG, where the PIT reference the calibration uses is itself emulated; real
hardware is unverified.

**Fixed** in `5129555`, and the calibration was not the culprit. `apic_timer_init`
correctly arms a ~1 kHz timer; the fault was the *time base*. Sleep deadlines were
expressed in `g_ticks`, which `sched_tick` increments on entry — and `sched_tick`
is entered by the hardware timer **on every CPU** and by all sixteen software
`int $0x20` yield sites. So `g_ticks` counted scheduler entries, running roughly
three times faster than wall time on a 2-CPU guest, by a factor that varies with
load. Deadlines now use the TSC, calibrated against the same PIT window
(`apic_now_tsc`/`apic_tsc_per_ms`). `sleep 30` measures 30.0 s.

### M21 — a software `int $0x20` acknowledges an interrupt that never happened
*code*

`sched_tick` calls `lapic_eoi()` unconditionally, but it is also the handler for
sixteen software `int $0x20` yield sites (`thread_yield`, `sched_sleep_ms`,
`mutex_lock`, the pipe-full yield, `sys_exit`, …). Each of those sends an
end-of-interrupt for an interrupt the LAPIC never delivered, which can retire a
genuinely pending one. The same conflation is why `g_ticks` is not a clock (see
`M18`).

Not fixed. The proper repair is to give voluntary yields their own vector with a
handler that neither advances the clock nor signals EOI, which means touching every
yield site; `M18` removed the urgency by moving timekeeping off `g_ticks`.

### H22 — Ctrl+C was delivered to whichever waiter polled first
*verified*

Introduced by the `H4` fix and caught by its own test. Once the Ctrl+C poll ran
every 50 ms, every `sys_waitpid` caller in a `login → shell → job` chain watched the
same console, and whichever peeked first claimed the keystroke — so `login` could
kill the shell instead of the job. Observed as `process_kill pid=71` where 71 was
the shell.

**Fixed** in `a7e6d20`: processes record whether they are waiting on a child
(`in_waitpid`) or reading the console (`in_console_read`), and a waiter claims a
Ctrl+C only when its target is doing neither — which is exactly the foreground job.
Three kills in three tries then hit the right pid.

### H23 — unexplained user fault returning from a successful spawn
*verified once, cause unknown*

One run out of eight faulted in the shell immediately after a `spawn` that had
succeeded:

```
exception vector=0x0e error=0x15 rip=0x401249 cs=0x33 cr2=0x401249 [user]
  rax=0x4b (75 — the new pid, so the syscall returned normally)
```

`error=0x15` is a user-mode *instruction fetch* on a page marked present, and
`0x401249` is the `ret` immediately after the `syscall` in the shell's `spawn`
wrapper — inside a segment the ELF loader maps executable. So a page that had been
executing fine became non-executable, or its tables were changed underneath it,
between the `sysret` and the next instruction.

Not reproduced in seven further runs and not attributed. The failure-path
`vmm_space_destroy` calls added in `9cbaaaf` were ruled out: the spawn returned a
valid pid, so none of them ran. A double-free of a page-table page (freeing one
address space while another still references it) would fit the symptom and is the
first thing to check if it recurs.

## Low

- **L14** — `stat` prints a literal `(%04o)`: tinylibc's printf has no `%o`
  conversion (`user/bin/stat.c:39`, `user/libc/src/stdio.c:106-120`). **Fixed** in
  `479d70e`: printf gained `%o`/`%lo` and a zero-pad flag, and `stat` renders the
  setuid/setgid/sticky bits symbolically as well.
- **L15** — `sys_read` on a socket spins forever if the peer never sends
  (`syscall.c:823`); no timeout. **Fixed** in `6b3c8ed`: `sys_read` and `sys_recv`
  poll on a 30 s budget, sleeping rather than spinning, then return -EAGAIN.
  Reasoned, not reproduced — arranging a silent peer needs a literal-IP fetch,
  which wget does not support.
- **L16** — `CLAUDE.md` drift: `sys_sleep` is described as a busy-wait but blocks
  properly (`sched.c:232-248`); `sudo` is documented as checking `/etc/sudoers`,
  which does not exist; the dead `ps2kbd_getchar`/`ps2kbd_ready` accessors are
  documented rather than deleted. **Fixed**: the `sys_sleep` and `/etc/sudoers`
  entries became true in earlier commits; the dead accessors (plus the driver's
  now-unused private ring and `ps2kbd_set_stdin_waiter`) are deleted. One further
  drift found while checking: `CLAUDE.md` claimed there was "no way to suppress
  terminal echo" while typing a password, implying passwords are echoed. They are
  not — `login` and `passwd` read a line via `read(0, ...)`, and nothing in the
  kernel echoes; the echo seen while typing commands is the shell's own.
- **L19** — `free` reports the size of the PMM's address span, not installed RAM
  (*verified*): on a 512 MiB VM it prints `total 64G, used 63G, free 501M`. The
  free figure is right; `sys_meminfo`'s total comes from the 64 GiB bitmap the PMM
  covers rather than the conventional memory the UEFI map actually reported.
  **Fixed** in `6b3c8ed`: `free` now reads 503M total / 498M free there.
- **L20** — userspace tool limits found while testing, both cosmetic: `grep`
  truncates any line past its 512-byte `LINE_SZ` (`user/bin/grep.c:6`), so piping
  a minified HTML page through it cuts the output; and `head` does not accept
  `-N`, treating `-2` as a filename (`head: -2: not found`). **Fixed** in
  `6b3c8ed`: grep's line buffer is 8 KiB, and head accepts `-N`, `-nN` and
  `-n N`.
- **L17** — `login` and `passwd` read only the first 2047 bytes of `/etc/passwd`;
  later entries are invisible (`login.c:18`). **Fixed** in `04f0eab` (8 KiB
  shared `pwdb.c` buffer, and it errors rather than silently dropping entries).
