# AetherOS audit — 2026-08-14

Baseline: `d8cee8f` (clean tree, ~19.4 kLOC C/H/asm).

The two previous audits (`audit-2026-08-11.md`, `audit-2026-08-12.md`) were
kernel- and security-focused and closed out ~30 findings between them. Both
explicitly recorded what they did **not** cover: ext2, AHCI/NVMe, xHCI/USB, the
GUI, ACPI and SMP bring-up. This pass went at that untouched surface, plus the
userland, the build, and CI — none of which had ever been audited.

Nothing already listed as fixed or as "checked and found sound" in the earlier
documents is re-litigated here.

Findings are numbered `P*` to keep them distinct from the `C/H/M/L` and `N`
series of the previous two passes.

---

## Critical

### P1 — `path_split` overflows a kernel stack buffer, from any user process

`kernel/fs/ext2.c`. `path_split()` bounded the leaf name (`name_len > 254`
returned false) but copied the **parent prefix** with no bound at all:

```c
uint32_t par_len = (uint32_t)(last - path);
if (par_len == 0) { parent[0] = '/'; parent[1] = '\0'; }
else { memcpy(parent, path, par_len); parent[par_len] = '\0'; }
```

Every caller declares `char parent[256]`. The path reaching it is up to 511
bytes: `sys_mkdir`/`sys_creat`/`sys_unlink`/`sys_rename` each copy `char
path[512]` from userspace, and `vfs_resolve` normalizes into a 512-byte buffer
whose overflow guard yields a *valid truncated prefix* rather than an error.

So `mkdir("/aaaa…(400 chars)/x")` writes ~145 bytes past the end of a 256-byte
buffer on the calling thread's kernel stack. The kernel is built
`-fno-stack-protector`, kernel stacks have no guard page (only the BSP's does),
and the overflow is fully attacker-controlled in both length and content —
directly over the saved registers and return address of `ext2_mkdir`'s frame.

Reachable from an unprivileged process with a single syscall; no setuid binary,
no race, no filesystem state required. `path_split` runs **before** any lookup,
so it does not matter whether the parent directory exists.

**Fixed.** `PATH_SPLIT_MAX` (256) is now defined once and used both for the
caller buffers and for the bound inside `path_split`, which rejects an overlong
parent the same way it already rejected an overlong leaf.

### P2 — killing the current process wedges the filesystem for every other process

`kernel/proc/process.c`, `process_kill()`.

```c
if (proc->thread && !sched_kill(proc->thread)) return;
process_close_all_fds(proc);        /* takes vfs_lock, does block I/O */
```

`sched_kill` only *defers* when the target holds a lock (`locks_held > 0`).
When the victim is the **currently running** thread and holds nothing — which is
exactly the state of a thread that has just taken a page fault, or called
`kill(getpid())` — it sets `t->state = THREAD_DEAD` and returns true. The
still-executing thread then walks into `process_close_all_fds` →`vfs_close` →
`mutex_lock(&vfs_lock)` → ext2 → AHCI polling, with interrupts enabled.

Any APIC tick in that window reaches `schedule()`, sees `cur->state ==
THREAD_DEAD`, hands the thread to the reaper and never resumes it. If it had
already acquired `vfs_lock`, the mutex is held by a corpse **forever**: every
subsequent filesystem operation on the machine blocks permanently. The reaper
then frees the 64 KiB kernel stack of a thread still linked in the mutex waiter
list.

The window is not narrow — the teardown does real block I/O, so it spans
milliseconds while a 1 kHz timer runs. Two reachable paths:
`x86_64_exception_dispatch` (any user segfault) and `SYS_KILL` with the caller's
own pid.

`sys_exit` already had the correct order: close fds, orphan children, publish
status, and only then mark the thread dead.

**Fixed.** `process_kill` now detects `proc->thread == sched_current()` and runs
the full teardown while still runnable before marking itself dead and yielding,
mirroring `sys_exit`. It does not return in that case, which is what both call
sites already expect.

## High

### P3 — `rm` on a directory silently corrupts the filesystem

`ext2_unlink` had no `S_ISDIR` check and there was no `rmdir` anywhere in the
tree — no `ext2_rmdir`, no `vfs_rmdir`, no syscall, no binary.

`rm /somedir` therefore: decremented `i_links_count` from 2 to 1 instead of to
zero (so the inode was never freed), left `.` and `..` in place pointing at a
detached inode, never decremented the parent's link count, and leaked every
block the directory owned. The directory entry disappeared from the parent while
the inode and its blocks stayed allocated and unreferenced. No error was
reported. `e2fsck` finds a filesystem with unattached inodes and a wrong link
count on the parent.

**Fixed.** `ext2_unlink` refuses a directory, and a real `rmdir` path now exists
end to end: `ext2_rmdir` (refuses non-directories, non-empty directories, and
the root inode; releases blocks and inode; returns the parent's `..` link) →
`vfs_rmdir` (with the same `may_mutate_at` permission gate as `unlink`) →
`SYS_RMDIR` (84, matching Linux) → `rmdir()` in tinylibc → `/bin/rmdir`. `rm`
now reports `is a directory (use rmdir)` rather than corrupting anything, and
handles multiple arguments.

### P4 — the doubly-indirect block tree is never freed

Both `ext2_truncate` and `ext2_unlink` walked `i_block[12]` (singly-indirect)
and stopped. `ext2_write` allocates `i_block[13]` for any file past ~268 KiB
with 1 KiB blocks, and nothing ever released it or the ~256 data blocks hanging
off each of its entries. Deleting or truncating a large file permanently leaked
most of its blocks — invisible to `df`, since the superblock free count was
decremented at allocation and never given back.

**Fixed.** A shared `free_inode_blocks()` helper (used by both paths) now
releases the direct blocks, the singly-indirect tree, and the doubly-indirect
tree. Triple-indirect remains unsupported, but `ext2_write` cannot allocate it
either, so there is nothing to leak there.

### P5 — a short read at spawn leaks kernel heap into the new process

`spawn_process` ignored `vfs_read`'s return value:

```c
void *buf = kmalloc((uint32_t)fsize);
...
vfs_read(vfd, buf, (uint32_t)fsize);     /* result discarded */
elf_load(buf, fsize, &result);
```

On a short read — an I/O error, or the file shrinking between the `vfs_file_size`
query and the read, which are two separate unsynchronized VFS calls — the tail of
the buffer stayed uninitialized kernel heap. `elf_load` then parsed it as program
headers and copied it into the new process's user pages. That is a kernel-heap
infoleak to userspace plus nondeterministic execution. `kernel.c` already checked
`nread == lsz` on the equivalent path.

**Fixed.** The read is now checked against the expected size and the spawn fails
with `-EIO` otherwise.

### P6 — `elf_load` trusts `e_phentsize`, and has no cap on total mapped pages

Two problems in the same loop:

`e_phentsize` was never validated. With `e_phentsize == 0`, `phdr_off =
e_phoff + i * 0` is constant, so the *same* PT_LOAD segment is processed up to
`e_phnum` (65535) times. `vmm_space_map` writes `pt[pti] = phys | flags` over any
existing PTE **without freeing the page under it**, and `vmm_space_destroy` later
frees only whatever the last write left. Each repeat therefore leaks a physical
page that nothing will ever reclaim — up to ~256 MiB per `spawn`, permanently,
from an unprivileged process.

Separately, `npages` derives from `p_memsz`, bounded only by the user address
range. A single segment declaring a 128 TiB `p_memsz` drives the allocation loop
until the PMM is exhausted — a whole-machine memory DoS reached well before the
`goto fail` unwind. There is no per-process page budget anywhere in the kernel.

**Fixed.** `e_phentsize` must be at least `sizeof(struct elf64_phdr)`, and a
running total of mapped pages is capped at `ELF_MAX_PAGES` (16384 = 64 MiB),
far above anything this system's programs need.

### P7 — user programs corrupt each other's SSE registers

`grep -rn 'fxsave\|fxrstor\|xsave' kernel/` returns nothing. The context switch
(`SCHED_ENTRY` in `sched_asm.asm`) saves the 15 general-purpose registers and the
`iretq` frame — no FPU or SSE state at all. `CR0.MP/EM/TS` and
`CR4.OSFXSR/OSXMMEXCPT` are never touched either; SSE works only because the UEFI
firmware left `OSFXSR` set.

The kernel is safe because it builds `-mgeneral-regs-only`. **User programs were
not**: `USER_CFLAGS` had no such flag, so GCC freely emitted `movaps`/`movdqu`
for struct copies and inlined `memcpy`. Two user processes time-slicing on one
CPU silently corrupt each other's XMM registers.

**Fixed (stopgap).** `-mgeneral-regs-only` added to `USER_CFLAGS`, with a comment
tying its removal to the scheduler actually saving FPU state. The real fix —
`fxsave`/`fxrstor` in the context switch — is on the roadmap below; it is
required before any floating-point userland is possible.

### P8 — `find` has never worked

`kernel/fs/ext2.c` emits **newline**-separated names from `listdir`
(`buf[written++] = '\n'`), and `/bin/ls` parses them that way. `/bin/find` walked
the same buffer with `strlen(p)` / `p += len + 1`, i.e. as if entries were
NUL-separated. The first `strlen` therefore spanned the entire buffer: `find`
printed one bogus path containing embedded newlines, then jumped past the end and
stopped. It produced no correct output in any invocation.

Three further defects in the same file would have surfaced the moment the
separator was fixed: `do_find` declared its listing buffer and its scratch buffer
`static` **inside a recursive function**, and assembled paths into a single
file-scope buffer — so descending into a subdirectory overwrote the parent's
listing and path mid-iteration. There was also no depth limit.

**Fixed.** Rewritten to parse newline-separated entries, to keep one listing
buffer and one path buffer per recursion level (in BSS — the user stack is only
16 KiB), to detect directories with `stat` rather than a second speculative
`listdir`, and to bound recursion at 8 levels. `listdir` filters `.` and `..` by
default, so there is no cycle risk.

### P9 — the last unprotected writer to the account database

`user/libc/src/pwdb.c`'s `db_store` opened `/etc/shadow` (or `/etc/passwd`) with
`O_TRUNC` and then issued a bare `write()`. `sys_write` returns the count that
actually landed, so a short write on a nearly-full disk left the account database
**already truncated and only partly rewritten** while returning `-1` to the
caller. `write_all` was added to tinylibc by the 2026-08-11 audit (finding M6) for
exactly this class of bug; this call site was missed.

**Fixed.** `db_store` uses `write_all`. (Writing to a temporary and `rename`-ing
over the target would be better still — `rename` exists — and is on the roadmap.)

## Medium

### P10 — `calloc` and `realloc` are unreachable; `geteuid`/`getegid` had no wrapper

`calloc` and `realloc` are compiled into `libc.a` but were never declared in
`user/libc/include/stdlib.h` (which declared only `malloc`, `free`, `atoi`,
`exit`). Any program calling them fails to compile. Both `README.md` and
`CLAUDE.md` advertise them.

Likewise `geteuid`/`getegid` exist as syscalls 107/108 and are listed in the
README, but tinylibc had no wrappers — so a setuid binary could not ask what its
effective uid was.

**Fixed.** Declarations added for `calloc`/`realloc`; wrappers and declarations
added for `geteuid`/`getegid`.

### P11 — userland was built without `-Werror`

`COMMON_WARN` gives the kernel `-Wall -Wextra -Werror`; `USER_CFLAGS` had
`-Wall -Wextra` only. Given how much of the userland is hand-rolled string and
buffer code, warnings there are worth at least as much as in the kernel.

**Fixed.** `-Werror` added to `USER_CFLAGS`; the tree builds clean with it.

## Confirmed, and since fixed

P12 and P13 were catalogued here as projects rather than patches, and were then
taken on in the two commits that follow this document. Their write-ups are kept
below as the record of what was wrong, each with a note on how it was resolved
and on the further bugs that fixing it exposed. P14-P19 remain open and are
carried into the roadmap.

### P12 — SMP is decorative: no AP ever runs a thread

`lapic_ap_init()` arms the AP's timer like this:

```c
uint32_t period = lapic_read(LAPIC_TIMER_INITCNT);   /* the AP's own register */
lapic_write(LAPIC_TIMER_INITCNT, period);
```

It reads **the AP's own** `INITCNT`, which is 0 after INIT — the BSP's calibrated
period is a local variable in `apic_timer_init` and is never exported. So the AP
writes 0, which *disables* the timer. Every AP reaches `sched_idle_loop()` and
halts forever. The boot log shows `sched: ap cpu=1` and then nothing, under
`-smp 2`.

This masks a second, worse problem: `ap_entry()` never executes `lidt`, `lgdt`,
`ltr`, or `syscall_init()` — all per-CPU state. An AP is still on the
trampoline's temporary 4-entry GDT (which has no user selectors), with a null
TR and an IDTR of base 0 / limit 0xFFFF, and with `EFER.SCE`/`STAR`/`LSTAR`
unset. The moment an AP actually ran a user thread it would fault with no
handler installed.

**Fixed.** The BSP now publishes the period it measured (`s_timer_period`) and
`lapic_ap_init` arms with that. `ap_entry` builds the per-CPU state an AP does
not inherit: its own GDT (a single shared GDT can only ever describe one TSS),
its own TSS with its own `rsp[0]` and IST1 double-fault stack, `lidt` for the
shared IDT, `syscall_init` for the per-CPU MSRs, and `cpu_enable_protections`.
Verified by a new `ktest [sched]` assertion that fails unless work actually
lands on more than one CPU: `threads observed on 2 of 2 cpus`.

Turning the APs on exposed two further bugs that had been unreachable while the
second core was dormant, both of which had to be fixed before SMP was stable:

- **Two CPUs on one kernel stack.** `schedule()` cleared `cur->on_cpu` while
  still executing *on cur's kernel stack* -- the switch only happens when the
  assembly stub runs `mov rsp, rax` after `schedule()` returns. Another CPU
  could dequeue and resume that thread inside the window, and the two CPUs then
  trampled one stack: a double fault with `rsp=0`, intermittently, in whichever
  suite happened to be running. The release is now deferred to
  `sched_finish_switch()`, which the stub calls immediately after the stack
  switch, and `rq_take` skips a thread still marked on-CPU (allowing the
  self case, where no switch occurs at all).
- **Idle threads were dispatchable with `rsp == 0`.** `thread_create_idle` left
  `rsp` at zero, "set on first preemption". That held only while an idle thread
  could never be *dispatched* before first being switched away from -- the run
  queue always held the current thread, so `rq_take` never returned empty. The
  fix above made it return empty, and loading `RSP=0` double-faults. Idle
  threads now get a real initial frame entering `sched_idle_loop`.

- **Console input was reordered across CPUs.** `console_fill()` drained COM1 a
  character at a time -- read one, push one -- with nothing held, and *two* call
  sites drain it: `sys_read`'s console path and `sys_waitpid`'s Ctrl+C watcher.
  On one CPU that is harmless. With two, they interleaved between the read and
  the push, so characters reached the input ring out of order: the userland test
  typed `/bin/rm /ktest_ud` and the shell received `/in/rm /ktest_ud`, with the
  `b` arriving after the newline and turning the *next* command into `btouch`.
  `input_push` has a lock, but it only protects the ring, not the read/push
  pair. The drain is now atomic. Worth noting that the userland session test
  added in the previous commit is what caught this -- no in-kernel assertion
  would have.

One more SMP defect surfaced immediately: `serial_write` locked only the
in-memory log ring, never the UART, so once two CPUs ran, output interleaved
mid-word (`sahci: found at yscall: SYSCALL/SYSRET enabled0:2.`) -- corrupting the
very log the smoke test greps. Whole messages are now emitted under a transmit
lock.

Measured: before these fixes, 4 of 5 boots panicked; after, 8 of 8 pass with
`2 of 2 cpus` every time.

**Fixing the timer alone would immediately triple-fault the machine.** The two
must land together, which is why they are a roadmap item and not a patch here.
Everything below in this section is currently latent for the same reason.

### P13 — no VMM locking, no TLB shootdown, kernel PML4 copied by value

`kernel/mem/vmm.c` has no lock of any kind. Two CPUs in `vmm_map` for addresses
sharing a PDPT/PD can both see the entry absent, both allocate a page table, and
both store — leaking one table and silently losing every PTE installed through
it. `heap_lock` does not help: `expand()` calls `vmm_map` holding only that,
while `elf_load`'s `vmm_space_map` holds nothing.

`vmm_unmap`/`vmm_protect` invalidate only the local CPU; `vmm_space_map` and
`vmm_space_destroy` invalidate nothing at all while freeing pages back to the
PMM. On a working SMP system that is a direct use-after-free through a stale TLB
entry. There is no IPI mechanism for cross-CPU work — `lapic_send_ipi` exists but
is used only for INIT/SIPI.

`vmm_space_create` also *copies* the kernel's PML4 entries [256..511] into each
new address space rather than sharing them. Any kernel mapping that later
populates a **new** top-level slot is invisible to every pre-existing process.

**Locking and shootdown fixed; the PML4 copy is not.** A `vmm_lock` now
serializes every page-table mutation in every address space. It is IRQ-safe,
because `schedule()` reaches `vmm_space_destroy` straight from the timer ISR, and
holding it with interrupts off also means the scheduler cannot preempt a CPU that
owns it. Lock order is `vmm_lock -> pmm_lock`; nothing takes them the other way,
since the PMM never calls the VMM.

Cross-CPU invalidation now exists: `tlb_shootdown_page()` (vector `0xfd`,
`kernel/arch/x86_64/tlb.c`) broadcasts to all other CPUs via the ICR's
"all excluding self" shorthand and waits for acknowledgements. Nothing on that
path disables interrupts, deliberately — a CPU that waited for acks with
interrupts off could be waiting on a CPU doing the same, and neither could ever
service the other. Callers must therefore not hold an IRQ-disabling lock across
it, and the VMM drops `vmm_lock` first. Where interrupts are already off (the
kernel test suites, which no other CPU races) the remote flush is skipped and
warned about once rather than risking a deadlock.

Two cases deliberately need no shootdown, and say so in comments: `vmm_map`
only ever replaces a not-present entry, and `vmm_space_destroy` tears down an
address space that only one CPU ever loaded — a process has exactly one thread,
and `schedule()` switches that CPU's CR3 away before the reaper runs, which
flushes the old space's non-global entries on that CPU. That reasoning needs
revisiting if a process ever gains a second thread.

**Still open:** the kernel half of the PML4 is still copied by value rather than
shared. Nothing in the tree populates a new top-level kernel slot after boot, so
it is latent, but pre-populating all 256 kernel PML4 entries with empty PDPTs at
boot remains the right fix and stays on the roadmap.

### P14 — setuid TOCTOU in `spawn_process`

The path string is resolved four separate times, each taking and dropping
`vfs_lock` independently: `vfs_file_stat` (execute permission), `vfs_file_size`,
`vfs_open` (the image actually read), and then `vfs_file_stat` **again** to
decide whether to grant `euid = fuid`. An attacker with write access to the
containing directory can swap the binary between the read and the final stat, and
the kernel executes their image while granting root from the original file's
inode. The setuid decision must come from the same inode that was read.
`sys_open` has the same shape (permission checked on one lookup, descriptor from
another).

### P15 — `process_find` returns an unreferenced pointer

It takes `proc_table_lock`, finds the struct, drops the lock, and returns a raw
pointer with no refcount. `SYS_KILL` then reads `victim->cred.uid` and calls
`process_kill(victim)`; the victim's parent can `waitpid`-reap and `kfree` it in
that window. Compounded by pid recycling, so a stale pid can name a different
live process.

### P16 — TCP has no receive reassembly, ignores the peer's window, verifies no checksums

An out-of-order segment is dropped **and not ACKed** (no duplicate ACK is
generated), so recovery waits for the peer's RTO. The peer's advertised window is
parsed on send and never on receive. Our own `rcv_win` is set once at connect and
never recomputed, so when the 4 KiB ring fills we keep advertising 4095 while
dropping data — the connection wedges. No receive path anywhere in the stack
(`tcp`, `ipv4`, `udp`, `icmp`) verifies a checksum, though `checksum.c` exists and
is used on transmit. The ISN is the constant `0x12345678`, and `tcp_close` frees
the slot immediately with no TIME_WAIT.

### P17 — every driver is a synchronous busy-wait with iteration-count timeouts

There is not one interrupt-driven block or network device. Every timeout in the
tree is a loop counter rather than a deadline (`for (volatile j < 200000) {}`),
so its meaning changes with CPU speed and optimization level — even though
`apic_now_tsc()`/`apic_tsc_per_ms()` already exist and the scheduler uses them.
`usb_msc` holds an **IRQ-disabling spinlock across an entire USB transaction**,
so interrupts are off on that CPU for the duration of every disk I/O, which
directly skews the LAPIC tick and TSC sleep deadlines.

AHCI never issues IDENTIFY, so `blkdev.sector_count` is 0 on every device and
**no LBA is ever range-checked**. The e1000 probe matches on PCI class alone
(`0x02/0x00`), so any Ethernet controller — virtio-net, rtl8139 — receives e1000
register writes. Ethernet frames shorter than 60 bytes are padded without zeroing
the padding, leaking the tail of the previous frame from a shared static TX
buffer onto the wire.

### P18 — no block cache anywhere

`read_block` does `pmm_alloc_page` → device read → `memcpy` → `pmm_free_page`
**per 1 KiB block, every time**. `read_inode` costs two of those and runs for
every path component of every lookup, stat, read and write; `may_traverse`
re-walks the path from `/` on every VFS call. A `stat()` of a four-component path
costs on the order of 30 physical disk reads. `write_super()` runs on every
single block and inode allocation and free. `ext2_read` re-fetches the indirect
block once per data block. Bitmap scans test one bit at a time in C, where the
PMM already does the same job word-at-a-time with `__builtin_ctzll`.

### P19 — other confirmed defects, not yet fixed

- **Directories are capped at 12 direct blocks, silently.** `ext2_lookup`,
  `ext2_list_dir`, `dir_add_entry` and `dir_remove_entry` all stop at `b < 12`.
  Past ~12 KiB of entries (roughly 300–500 files) new files become invisible to
  lookup, and `dir_add_entry` frees the block it just allocated and returns
  false. `ls` and the shell truncate long listings independently on top of that.
- **`i_blocks` is computed from pointer slots in the inode**, not from allocated
  blocks, so it is wrong by orders of magnitude for any file with indirect
  blocks. `e2fsck` flags every such inode.
- **No timestamps, because there is no clock.** `ext2_create` zeroes the inode and
  nothing ever sets `i_mtime`. There is no RTC driver in the tree and no
  `gettimeofday`/`time` syscall, so `st_mtime` is structurally always 0.
- **No mount-time feature-flag validation.** `ext2_mount` checks only `s_magic`
  and the block size; `s_feature_incompat` is never read, so an ext3/ext4 volume
  mounts and its extent trees are misread as block pointers.
- **`VFS_MAX_OPEN` is 16 system-wide**, in a global table indexed directly by the
  process's fd, with no per-open refcount — which is precisely why `dup`/`dup2`
  and `lseek` cannot be implemented as things stand.
- **`vfs_file_size`/`vfs_file_stat`/`vfs_chown`/`vfs_chmod` skip `may_traverse`**,
  unlike every other VFS entry point. Safe today only because the syscall layer
  re-checks; any future in-kernel caller gets no check.
- **`mutex_unlock` has no ownership check** and decrements `owner->locks_held` —
  i.e. the wrong thread's counter if anyone unlocks a mutex they do not hold.
  `mutex_lock` also unconditionally `sti`s on the contended path, so a caller
  that entered with interrupts disabled silently gets them back.
- **`fd_set` overwrites a table slot without closing what was there**, leaking the
  previous descriptor; used when installing pipe ends at fds 0/1.
- **The shell's builtins shadow strictly better `/bin` binaries.** `ls -l` calls
  `listdir("-l")`, gets an error, and prints *nothing at all* — no output, no
  error — while `/bin/ls` implements `-l` and `-a` and is unreachable. `cat a b`
  fails the same way. There is no quoting, no globbing, no `&&`, and `>`
  redirection works only inside the `echo` builtin.
- **`readline` has no EOF path**: if `read(0, …)` keeps returning ≤ 0 the shell
  spins in an unbounded busy loop.

## CI and documentation gaps

Everything in this section except the version-string and `CLAUDE.md` items was
fixed in the commit that gave CI teeth (see the Status section).

- **The boot smoke test never greps for a panic.** It checks for
  `kernel: initialization complete`, the absence of `ktest: FAIL`, and the
  presence of `ktest:`. A kernel that initializes, passes every assertion, and
  then triple-faults on the login path **passes**. Finding H23 of the 2026-08-11
  audit was exactly such a post-init user fault. This is the cheapest available
  CI improvement.
- **`status=$?` is captured and never used**, so a QEMU crash and a clean timeout
  are indistinguishable.
- **Zero userland coverage.** CI never logs in and never runs a single `/bin`
  program. Every finding in P8 and P19 was invisible to it — `find` has never
  worked and CI stayed green for its entire existence.
- **`ktest:` presence is asserted but not the count**, so a run of 3 assertions
  passes as readily as a run of 8554.
- **The release workflow never boot-tests the artifact it ships.** It does not
  install QEMU or OVMF and never runs `make test`; it triggers on push to
  `master` in parallel with CI, so a red CI does not block a release. No
  checksums or signatures are published for images users are told to `dd`.
- **`check-deps.sh` omits `parted`, `mkfs.ext2` and `debugfs`**, which `make
  disk`/`make usb` hard-require and which the README lists as requirements — so
  the documented "verify tools" step passes and the build then dies.
- **README overclaims.** It presented `cd /bin && ls cat` as a working session
  transcript (the shell has no `&&`; `cd` receives the literal string
  `/bin && ls cat`), listed `>` redirection as a general shell feature when it
  works only inside the `echo` builtin, advertised `calloc`/`realloc` and
  `geteuid`/`getegid` that userland could not actually call (P10), and still said
  authentication was against `/etc/passwd` — it has been `/etc/shadow` since
  `04f0eab`, which the 2026-08-11 audit fixed in `CLAUDE.md` only. **All of these
  are corrected in this commit**, along with the program count and the new
  `rmdir`.
- **Three version strings, none derived from a common source**: `/bin/uname`
  reports "AetherOS 1.0", the shell builtin says "2.0", and releases are at
  v2.10.x. Not fixed here — it wants a generated header.
- **`CLAUDE.md` is gitignored**, so its accurate "Known Limitations" section is
  not public and the README is the only public document — the one with the stale
  claims.

## Roadmap

Ordered by what unblocks the most. The first group is correctness work the rest
depends on; the second is the feature direction.

### 0. Prerequisites (do these before any feature work)

1. ~~**Make SMP real (P12).**~~ **Done.** APs now get a real timer period and
   full per-CPU state; `ktest` asserts threads land on more than one CPU.
2. **VMM lock + TLB shootdown + pre-populated kernel PML4 (P13).** Lock and
   shootdown are **done**. Still outstanding: allocate 256 empty kernel PDPTs at
   boot so the kernel half of every PML4 is *shared* rather than snapshotted.
   Prerequisite for demand paging, COW, `fork` and `mmap`.
3. **FPU state in the context switch (P7).** `fxsave`/`fxrstor` in `SCHED_ENTRY`
   plus a state area in `struct thread`, then drop `-mgeneral-regs-only` from
   `USER_CFLAGS`. Required before any floating-point userland. **Now the most
   valuable remaining prerequisite**, since two user processes really do share a
   CPU pool now.
4. ~~**CI with teeth.**~~ **Done.** The boot test fails on any fault, asserts the
   ktest count, and checks qemu's exit status; a scripted login session exercises
   userland; the release gates on all three and publishes checksums.
5. **Per-CPU run queues.** A single global `rq_lock` is now taken from every
   CPU's timer ISR on every tick. It is correct, but it is the obvious next
   scaling limit now that more than one CPU actually runs threads.

### 1. Storage and filesystem depth

- **A block cache (P18)** — even a 64-entry LRU keyed on block number retires the
  per-block `pmm_alloc_page`/`memcpy`/`free`, and with it most of the reason
  `vfs_lock` has to be global. Highest performance return in the tree by a wide
  margin.
- **Indirect-block directories (P19)** — lift the silent ~500-file ceiling.
- **Correct `i_blocks`, real timestamps** (needs the RTC below), **feature-flag
  validation at mount**, and a **cache-flush command** on the AHCI/NVMe/USB paths
  so the drive's own write cache is committed.
- **`struct file` with refcounts**, replacing the 16-entry global open table —
  this is the single change that unlocks `dup`, `dup2`, `lseek`, and `fcntl`.
- **A real `blkdev_register` + `fs_register` + mount table.** `blkdev_t` is
  already a clean 4-function vtable, but `vfs_init` hardcodes three static
  instances and calls `ext2_*` directly on one global filesystem. The
  path-resolution and permission layer above it is already fs-independent and
  would sit unchanged on top. Prerequisite for a second filesystem — and for
  `/proc` and `/dev`, which would in turn retire the bespoke `SYS_PS`,
  `SYS_MEMINFO` and `SYS_DISKINFO` syscalls.
- **`pmm_alloc_contig(n)` + PRD/PRP lists** to lift the hard 4 KiB-per-command
  ceiling every block driver currently has, and **populate `sector_count`** so
  LBAs are finally range-checked.

### 2. POSIX kernel surface

- **`gettimeofday`/`time` + an RTC/CMOS driver.** Nothing in the system knows the
  wall-clock time; this blocks file timestamps, `ls -l` dates, `date`, and any
  meaningful log. Small, self-contained, and unblocks a lot.
- **`lseek`, `dup`/`dup2`, `fstat`, `getdents`, `umask`, `fsync`** — mostly
  gated on the `struct file` refactor above. `dup2` in particular is what
  generic shell redirection needs.
- **A VMA list on `struct process` + a page-fault handler**, in that order:
  demand paging → stack auto-growth → copy-on-write → `fork` → `mmap`. The
  fault hook slots into `x86_64_exception_dispatch` immediately after the
  existing extable check. This is the largest single architectural gap.
- **Real signals**, retiring the polled Ctrl+C: a pending mask on the process,
  delivery at syscall return (where the deferred-kill unwind already lives), and
  process groups / sessions so the foreground job is a fact rather than the
  `in_waitpid`/`in_console_read` heuristic.
- **Fix the TOCTOU and lifetime bugs (P14, P15)** — decide setuid from the opened
  inode, and refcount processes.

### 3. Usability: editor, shell, libc

- **A text editor.** With `>` redirection working only inside `echo`, the only
  way to create or modify a file on the running system is `echo text > file`, one
  line at a time, with no quoting. A small `ed` is ~200 lines against the current
  libc and would change the character of the system more than anything else on
  this list.
- **Shell: quoting, escaping, globbing, `&&`/`||`/`;`, real redirection for
  external commands and pipelines (`>`, `>>`, `<`, `2>`), and `$?`.** Stop
  builtins from shadowing better `/bin` binaries — at minimum fall through when
  an argument starts with `-`, which today makes `ls -l` print nothing at all.
  Then tab completion and cursor movement in `readline`.
- **An environment.** `envp` through `sys_spawn` → `crt0` → `getenv`, which is
  what `$PATH`, `$HOME`, `$PS1` and `env`/`export` all need.
- **tinylibc: `FILE*` (`fopen`/`fgets`/`fprintf`), `errno` + `perror`, `getopt`,
  `qsort`, `ctype.h`, `memmove`, `strtok`, `dirent.h`.** `errno` matters most:
  syscalls already return negative errno values and the wrappers throw them away,
  which is why `cat` reports "no such file" for a permission denial. `memmove`
  matters second — `memcpy` is a forward byte loop, so any editor-style buffer
  insert silently corrupts. `stderr` does not exist anywhere, so error messages
  currently flow into pipelines as data.
- **Missing coreutils**, cheapest first: `echo` as a binary (it exists only as a
  builtin, so `echo x | tee` is impossible), `tee`, `basename`, `dirname`, `seq`,
  `yes`, `true`/`false`, `du`, `sha256sum` (the SHA-256 implementation is already
  in libc and FIPS-tested), then `more`, `tr`, `cut`, `uniq`, `xargs`, `diff`,
  `tar`. Also `/etc/group`, which does not exist — `id` currently works around it
  by assuming gid == uid.

### 4. Networking depth

- **Verify checksums on receive** — the smallest correctness fix in the stack.
- **Out-of-order queue + duplicate ACKs; recompute `rcv_win` from ring
  occupancy; parse and honour the peer's window** (P16). Together these turn a
  connection that wedges under loss into one that recovers.
- **Randomize the ISN; add TIME_WAIT.**
- **Per-connection locking** — `tcp_input` runs on the net thread and mutates
  state that the user thread reads concurrently.
- **A retransmit timer thread**, so `send_reliable` stops blocking its caller for
  up to ~9 s, and per-connection RTT estimation instead of a fixed 300 ms RTO.
- **TCP server side** (`bind`/`listen`/`accept`) — the stack is client-only today.
- **Userland**: `ping` (the kernel already has `icmp.c`; it needs one syscall),
  `nslookup` (`dns_resolve` is already a libc call — ~20 lines), and `ifconfig`
  (needs a syscall exposing the DHCP lease, following the `free`/`df` pattern).
- **Driver hygiene**: match e1000 on vendor/device ID rather than PCI class, and
  zero the Ethernet pad bytes that currently leak kernel memory onto the wire.

## Follow-up pass, 2026-09-10

A later session went back over the must-fix list. Fixed and committed since:

- **P14 — setuid TOCTOU.** `spawn_process` now opens once and derives the
  execute check, the size, the image bytes and the setuid credentials from that
  one descriptor via a new `vfs_fstat`, instead of resolving the path four
  separate times. This was a local privilege escalation.
- **P15 — `process_find` handed out unreferenced pointers.** Replaced by
  `process_find_ref`/`process_put` with a refcount, plus `process_exists` for
  callers that only need a liveness check. The struct is freed by whichever of
  `process_reap` and the last `process_put` runs second.
- **P7 — no FPU state in the context switch.** Each CPU now enables
  `CR4.OSFXSR`/`OSXMMEXCPT`, clears `CR0.EM` and runs `fninit`; every thread
  carries a 512-byte `FXSAVE` image swapped on each real switch. Note the
  alignment cannot be delegated to `kmalloc`: its 40-byte header leaves every
  allocation 8-byte aligned, so the area carries slack and is aligned by hand.
- **P19 — directories capped at 12 direct blocks.** Directory layout now lives
  in `dir_block_count`/`dir_block_at`/`dir_block_append` and every walker goes
  through them, so the singly-indirect block is followed everywhere. Previously
  a directory past ~12 KiB kept accepting files that were then invisible to
  lookup and listing — silent partial data loss.
- **P19 — `i_blocks` counted inode pointer slots** rather than allocated blocks,
  so it was wrong by orders of magnitude for any file with indirect blocks and
  `e2fsck` flagged every one. `count_inode_blocks` walks the tree.
- **`THREAD_DEAD` was not actually terminal.** `sched_sleep_ms` and `mutex_lock`
  both stored `THREAD_BLOCKED` unconditionally, so a thread killed just before
  blocking overwrote its own `DEAD` state, went on the sleep list, had its
  deadline expire, and was promoted back to `READY` and resumed. Both refuse to
  block a dead thread now.
- **Mutex waiter list aliased `thread->wait_next`** with the process wait queue,
  so a thread on both lists truncated one of them. It has its own `mutex_next`.
- **`mutex_unlock` dropped wakeups**: it popped one waiter and called
  `sched_wake`, which silently does nothing for a thread that is not
  `THREAD_BLOCKED`. It now retries until one is genuinely promoted.

### Open: intermittent loss of progress under mutex contention

Not fixed, and characterised rather than guessed at. `ktest [sched]` fails
roughly 1 boot in 15-20 with `mutex_counter == 20U`, and `ktest [vfs]`
occasionally with `finished == VFS_STRESS_THREADS`. Instrumented captures show
a consistent signature:

```
counter=15  iters=4/10   thr0 BLOCKED  thr1 DEAD   mutex locked=0 owner=none waiters=(none)
counter=16  iters=10/5   thr0 DEAD     thr1 BLOCKED mutex locked=0 owner=none waiters=(none)
```

What that establishes:

- **Mutual exclusion is intact** — an overlap counter incremented inside the
  critical section never fires, so no two threads are ever inside at once. The
  lost counts are lost *progress*, not lost increments.
- **One thread ends `THREAD_BLOCKED`, off the mutex's waiter list, while the
  mutex is unlocked and unowned.** Nothing can ever wake it: `mutex_unlock`
  only wakes threads it finds on the list. The invariant *"a thread blocked on a
  mutex is either on that mutex's waiter list or runnable"* is violated.
- It is symmetric — either thread can be the one that loses.

A third capture added counters for the obvious mechanisms, and **all three read
zero**:

```
counter=12 iters=10/1 overlap=0 dbl_enq=0 unlisted=0 wake_drop=0
```

That rules out, with evidence rather than argument:

- **A self-looped waiter list** (`dbl_enq=0`). Enqueueing a thread already on the
  list would point its `mutex_next` at itself and orphan everything behind it,
  producing exactly the observed state. It never happens.
- **Taking the lock while still queued** (`unlisted=0`), which is how a thread
  would come to be double-enqueued in the first place.
- **`mutex_unlock` dropping a wakeup** (`wake_drop=0`). Every pop was followed by
  a `sched_wake` that genuinely promoted the thread to `THREAD_READY`.

So the stuck thread *was* made runnable, and then later ended up
`THREAD_BLOCKED` while on neither the mutex waiter list nor holding the lock.
The current code has no path that produces that: the only writers of
`THREAD_BLOCKED` are `mutex_lock` (immediately after linking onto the waiter
list) and `sched_sleep_ms` (immediately after linking onto the sleep list), and
`mutex_thread` never sleeps.  Either one of those invariants is violated by a
path not yet found, or `state` is being written/observed inconsistently -- it is
a plain `thread_state_t`, written outside `rq_lock` in several places, which the
original audit flagged separately.

Two further details no hypothesis covers: the counter is consistently one higher
than the recorded iterations account for, and the stuck thread's iteration count
varies widely (1, 4, 5 of 10) rather than clustering near the end.

Suggested next step: instrument every write to `thread->state` with the writer's
identity, rather than sampling the state after the fact.  Sampling has now
eliminated the mechanisms it can reach.

The three fixes above were each individually justified but none changed the
rate: 3 failures in 65 boots before, and still failing after. Whatever drops the
wakeup is elsewhere in the block/wake path.

Worth recording how this became visible at all: the test suites used bare
`while (cond) { thread_yield(); }` waits, so every rare race surfaced as a
60-second CI timeout with no indication which of a dozen waits was stuck.
Bounding them on the wall clock turned those hangs into named assertions, which
is what made two of the bugs above findable. Any further work here should keep
that property.
